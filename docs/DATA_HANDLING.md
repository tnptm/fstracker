# Data handling and GDPR

This is the operator's reference for how fstracker treats personal data. The user-facing text is the
privacy policy page (`frontend/app/(legal)/privacy/page.tsx`, served at `/privacy`). If the two ever
disagree, fix the code or the page so they match.

Principle: collect the minimum, use it only to run the app, never share it, let users export and delete
it themselves, and delete it when it is no longer needed.

## Anonymous accounts

Sign-up asks for a password only. The server creates a random 12-character username (`accounts/usernames.py`,
about 59 bits, no look-alike characters) and shows it once after sign-up and later under Account. Login accepts
any casing. There is no email, so there is **no password reset**: a lost username or password means a lost account,
and the sign-up and policy texts say so. Do not add fields that identify people (name, email, phone) without a
clear purpose and a policy update. If you ever add email (for example for password reset), make it optional and
update the data inventory, export, policy and `POLICY_VERSION`.

## Roles and legal basis

- **Controller:** the person running the service (`frontend/lib/privacy.ts`: `CONTROLLER_*`). Set a contact
  email there so users have a direct way to reach you.
- **Legal basis:** Art. 6(1)(b) (providing the app the user asked for) for account and volunteer data;
  Art. 6(1)(f) (security) for technical logs and rate limiting. The sign-up checkbox records that the user
  has read the policy. It is **not** the legal basis and there is no marketing or tracking consent.
- **Third parties:** none. No analytics, ads, email service, external fonts or error trackers. Fonts are
  self-hosted by `next/font` at build time.
- **Hosting provider:** if the VPS or Docker host belongs to a hosting company, that company technically
  hosts the data. Use a provider with a data processing agreement and servers in the EU/EEA, or document
  your own safeguards. Do not add services that receive user data without updating this file, the privacy
  policy and its version.

## Hosting and processor assessment

Recorded assessment (not legal advice): this is a public demo that mostly serves its owner. Users are not required
to give real data: accounts are anonymous (a random username generated by the server and a password, no name or
email). IP addresses in server logs and anything users type into comments can still be personal data, so the GDPR
applies and the rest of this document stays in force. The data lives on a VPS that the controller
administers; the hosting company provides hardware and network only, does not read the contents and does not make
backups. Backups are not enabled; if they are, the controller makes them and keeps them on its own systems.

Open points: no written confirmation or data processing agreement from the hosting company yet (an infrastructure
provider can still count as a processor under the EDPB's view). Ask for the provider's DPA or a written statement,
and file it. Revisit this section if a backup destination, mail service or any other service is added.

## Data inventory

| Data | Where | Purpose | Retention |
|---|---|---|---|
| Random username, password hash, `date_joined`, `last_login` | `auth_user` | Account and login. No email or name is collected | Until account deletion or inactivity limit |
| Legacy `email` (accounts created before sign-up became anonymous) | `auth_user` | Not used for anything; the user can remove it under Account | Until removed or the account is deleted |
| `first_name`, `last_name` | `auth_user` | Not collected by the app (always empty) | Same |
| Time entries, day notes, goals, courses (with comments) | `tracker_*` | The app's main function | Same |
| Policy acceptance (version, timestamp) | `accounts_policyacceptance` | Proof the user was informed | Deleted with the account |
| JWT ids (no personal data) | `token_blacklist_*` | Session revocation | Deleted at logout, expiry, or account deletion |
| IP, user agent, URL, time | gunicorn/Docker logs, nginx logs | Security and debugging | Docker: capped at 3 × 10 MB; nginx: logrotate (keep short, e.g. 14 days) |
| IP rate-limit counters | Django cache (memory) | Sign-up abuse protection | About 1 hour, lost on restart |
| `access_token`, `refresh_token`, `csrftoken` cookies | Browser | Login session, CSRF protection | 15 min / 30 days / session. Strictly necessary, no consent banner needed |
| `theme` | Browser local storage | Light/dark choice | Until cleared. No personal data |

Database backups (`deploy/backup-db.sh`) would contain all of the above and rotate (default: newest 14). **Backups are
not enabled at the moment**; the privacy policy says so. If you start making them, keep them on your own systems
and check the policy text (section 6) and the hosting note below.

## Data subject rights

| Right | How the user exercises it | Where in code |
|---|---|---|
| Access, portability (Art. 15, 20) | Account → Download my data (JSON) | `GET /api/auth/me/export/`, `accounts/export.py` |
| Rectification (Art. 16) | Edit entries, notes, goals and courses in the app. The random username is not editable; a legacy email can be removed under Account | `PATCH /api/auth/me/` (`{"email": ""}`) |
| Erasure (Art. 17) | Account → Delete account (password required) | `DELETE /api/auth/me/` |
| Restriction, objection (Art. 18, 21) | Contact the controller | Manual, see below |
| Information (Art. 13) | Privacy policy page, linked from sign-up, login and the Account page | `/privacy` |

Manual requests: verify the requester controls the account, answer within **one month**, and delete or
export via the Django admin (`/admin/`) or `manage.py shell` if the user cannot log in. Erasure by deleting
the `User` also removes everything they own (foreign keys cascade). Delete their `OutstandingToken` rows
first, as `accounts/views.py` does.

## Retention

- Accounts and data stay until the user deletes them.
- **Inactive accounts** (no login or session refresh for `DJANGO_INACTIVE_ACCOUNT_MONTHS`, default 24) are
  deleted by `manage.py enforce_retention`, which also flushes expired token rows. Staff/superuser accounts
  are skipped. **You must schedule it**, for example daily:

  ```bash
  15 4 * * * cd /opt/fstracker && docker compose --env-file .env.prod -f compose.prod.yaml exec -T backend python manage.py enforce_retention
  ```

  Try `--dry-run` first. If you change the months, also update `INACTIVE_ACCOUNT_MONTHS` in
  `frontend/lib/privacy.ts` (it is shown on the policy page).
- **Backups** are currently not made. If enabled, they roll off by `KEEP` (default 14 daily dumps), so deleted data
  leaves backups within about two weeks. If you restore a backup, re-apply any erasures made since it was taken.
- **Logs:** keep nginx access logs short (logrotate, e.g. 14 days). Do not add personal data (email,
  usernames, request bodies) to application logs. The retention command logs only user ids.

## Policy versions

`PRIVACY_POLICY_VERSION` (`backend/config/settings.py`) and `POLICY_VERSION` (`frontend/lib/privacy.ts`)
must match. Bump both, plus `POLICY_UPDATED`, when the policy changes in a way users should re-read. Users
who have not accepted the current version see a notice in the app and can accept with one click
(`POST /api/auth/privacy/accept/`). New users accept at sign-up (`accept_privacy` is required).

## Rules for contributors

- A new field or model that holds personal data must: be scoped to the user and cascade-delete with them,
  be added to `accounts/export.py`, be listed in the data inventory above and in the privacy policy, and
  have a retention rule.
- Do not send user data to external services, and do not add trackers, analytics or third-party scripts.
- Do not put personal data in logs, URLs or error messages.
- Keep collecting only what the app needs (data minimisation). Do not start asking for names, phone
  numbers and similar without a clear purpose.

## Security measures

HTTPS (nginx), salted password hashes (Django), HTTP-only cookies, CSRF protection, per-user data scoping,
rate limits on sign-up and login, containers publishing ports on `127.0.0.1` only, non-root containers
(`deploy/README.md` has more).

## Personal data breach procedure

If personal data may have been exposed: contain it (rotate `DJANGO_SECRET_KEY` and the database password,
fix the cause), record what happened, and if it risks users' rights notify the supervisory authority
within **72 hours** of becoming aware (Finland: Office of the Data Protection Ombudsman, tietosuoja.fi)
and the affected users without undue delay if the risk is high.
